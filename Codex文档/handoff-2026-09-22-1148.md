## 1. ⚠ 修了一个实机安全缺陷（最重要）

**板间链路掉线后，底盘不会进入 zero force，而是拿断链瞬间的陈旧摇杆值一直算力矩发出去。**

`Chassis/User_File/5_Task/task_remote.c` 里 `remote` 是 `Remote_Task_Entry` 的跨循环
局部变量，原先唯一的清零点挂在 `state.online != 0U` 上。而 `state.online` 只由本地
UART5 帧驱动——**接收机装在云台板，底盘 UART5 永远收不到帧**，所以它恒为 0，
那个 `memset` 永不执行。`Board_IsOnline()` 返回 0 只是停止覆盖 `remote`，
于是它整个停在最后一帧上，`online` 还是 1，底盘一路绿灯。

修法是加一个 `else if (state.online == 0U)` 分支显式清零。**写成 else-if 而不是
无条件 else**，因为底盘真插了 DR16 时板间掉线应该回退到本地遥控，不能把它抹掉。

⚠ **这条的验收判据必须上实机**：拔掉 FDCAN3 线，看 `Chassis.remote_online_flag`
归零、`CHASSIS_FAULT_REMOTE` 置位、`output.T_joint` 与 `I_wheel` 全零。
主机单测覆盖不到——`task_remote.c` 要 HAL + FreeRTOS，编不了。

## 2. 阻塞项消解：不用换三档开关

上一份把"i6X 只有一个三档、底盘需要两个"列为模式分配的阻塞项，并列了
换开关模块 / 挪通道 / 混控三条出路。**一条都不用走。**

用户给的方案把"允不允许动"和"做什么"重新切分：三档只用在使能级（SwC）上，
模式改由 **VrA 选组 + SwA/SwB 两档** 表达，正好落在出厂硬件能给的范围内。
`Gimbal/CLAUDE.md` 里那一整节出路分析已改写，别再照着它去拆遥控器。

## 3. 计划外的几个决定（都改了原计划）

### 3.1 删掉了 `remote_mode_request_t` / `remote_leg_request_t` 整套中间层

原计划只改 `Remote_t` 的字段。实际动手时发现 `Chassis_Remote_Update` 里那个
7 分支 switch 纯粹是 `REMOTE_MODE_*` → `CHASSIS_MODE_*` 的同义翻译，属于风格规范
点名要删的封装层。于是拨杆直接映射到 `Chassis_Mode_t`，两个枚举和两个字段全删。

**副作用是好的**：`remote_input.h` 退化成纯输入类型，**两块板逐字节相同**，
少一个已知漂移源。`Chassis/User_File/1_Middleware/0_Common/remote_input.c` 因此变空、
已删除，`Chassis/CMakeLists.txt` 和 `test_dr16` 配方同步撤掉了它。

映射表现在是 `chassis_remote.h` 的 `CHASSIS_MAP_*` 宏。

### 3.2 没有实现跳跃锁存

用户选定的语义是"跳跃完成后锁存 STANDING，SwB 拨回 UP 才解锁"，原计划也写了
要加 `Chassis.jump_latch_flag`。**实际没加。**

理由：跳跃状态机还没写，`Chassis_Remote_Update` 收到 `JUMP` 时直接回落 `FOLLOW`，
锁存**没有触发源**，写了就是死代码，违反"不为未来扩展预留设计"。
语义和实现要点记在 `遥控键位与模式分配.md` §5.1，跟状态机一起落地。

### 3.3 急停和掉线时 `Chassis.mode` 保持不变，不压成 ZERO_FORCE

原计划的验收判据写的是"上电四杆全 UP → `Chassis.mode == CHASSIS_MODE_ZERO_FORCE`"。
**动手时发现这么做是错的**：`CHASSIS_MODE_ZERO_FORCE` 在 `Chassis_State_Update`
（`chassis_control.c:637`）里会把 `Chassis.fault` **整个清零**，连
`CHASSIS_FAULT_REMOTE` 一起抹掉——那样 §1 修的东西在 Watch 上就看不出来了。

所以保持原有语义：急停/掉线只关许可 + 回中目标，模式不动，封输出交给 fault 路径。
**判断"是不是急停/掉线"要看 `remote_stop_flag` 和 `fault`，不要看 `mode`。**
`test_chassis_remote.c` 的 `testOffline` 钉死了这条，注释写了理由。

### 3.4 自瞄 flag 只做了一半

`APP_BOARD_FLAG_AUTOAIM` 的设计语义是"自瞄**实际**激活"（拨杆在位 **且** 上位机在线），
因为上位机掉线时 SwD 打下去不该让底盘锁航向。**当前只实现了拨杆那一半**：
`task_usb` 只有累计计数器、没有最近一帧的时间戳，补在线判定属于自瞄那一摊活。
代码和文档里都标了。

## 4. 板间协议变了

状态帧 `0x4` 整个重排。**改协议后必须跑 `Gimbal/Real/Tests/test_board_protocol.c`。**

新增的两个用例值得留着：

- `test_switch_slots_independent` —— 一次只拨一路，确认位域不串扰。
  **全设成同一个值的往返测试抓不到移位写错**，这条能抓到（已做变异验证：
  把解包移位从 `index*2` 改成 `index`，用例立刻红）。
- 预留字节 `state[5]` 必须填零的断言。

`knobB`（VrB）**不下发底盘**——摩擦轮和拨盘纯属云台事务。测试里专门断言了
底盘侧 `rx.knobB == 0`，防止将来有人顺手把它塞进协议。

FDCAN3 是 `FDCAN_FRAME_CLASSIC`，**8 字节封顶**，状态帧现在用了 7 个，剩 1 个预留。
要加字段先想清楚，扩到 FD 要重新过 CubeMX 并重算两条总线的位定时。

## 6. 还欠什么

### 本轮引入的

1. **`APP_RC_LEG_CROUCH` 现在等于 0.18，即"压缩腿"实际不压。** 真实压缩量要等
   跳跃蓄力实现时按实机定——提前填一个猜的值只会让人以为它调过。
2. **`APP_RC_TRIGGER_ON = 0.979`（对应 VrB 1990 us）没实测过端点。**
   用户说 VrB 确定能到 2000，但这个区间只占量程 1%，上机第一件事是拧到底读实际值。
3. **`Gimbal/Debug` 没有同步**，和上一轮一样。它有独立的 `User_File` 副本。

### 上一轮继承的（都还在）

4. **云台 `APP_DM_TOR ±10` 仍未与 DM4310 的 TMAX 寄存器核对。** 判据见根
   `CLAUDE.md` §DM MIT torque scale——**不能靠比对命令和反馈，必须用绝对力参照**。
5. 底盘那两个未经实机验证的调参：`APP_RC_MAX_VEL` 1.0→2.0、`spin_d_fai` 3.14→9.42。

### 长期计划（只预留了名字）

跳跃、自瞄、摩擦轮/拨盘三项的现状、已有基础设施、缺什么，逐条记在
`遥控键位与模式分配.md` §5。三项的底层其实都齐了：
发射机构的设备层和 CAN 槽位在、上位机 `{yaw, pitch, shoot}` 协议在，
缺的都是控制逻辑本身。

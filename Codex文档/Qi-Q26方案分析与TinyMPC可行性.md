## 〇、最重要的发现：他独立诊断出了和你一模一样的根因

原文（技术背景概述 1）：

> 「在更改为串级 PID 控制腿长之后，抗干扰能力有了明显的提升，但是 Roll 轴不能得到很好的补偿。
> **洞悉本质，我发现了当系统的腿长一定的时候，车身的 Roll 角也一定是唯一确定的，
> Roll 角补偿的 PID 与腿长控制的 PID 会相斥**，所以该控制方案不能够很好地补偿 Roll 轴偏移。」

这和我在 `chassis_control.c` 里给你诊断的是同一件事。他的解法也和我的建议一致——**换状态变量**：

> 「在选取状态变量时，**不选取单一一侧腿长为状态变量**，而是通过转换得到车身中轴线相对
> 地面的高度 H 和 Roll 角 α 作为状态变量，**这样既可以避免了在 PID 方案中的输出量相斥的问题**。」

**这条独立佐证很重要**：说明这不是我的臆测，是这类机器人的共性坑，而且解法明确。

## 一、他到底做了什么（两层双速率架构）

| 层 | 算法 | 周期 | 管什么 | 输出 |
|---|---|---|---|---|
| 腿部 | **轻量化线性 MPC** | **0.01 s（100 Hz）** | 车身高度 H + Roll 角 α | `F_Nl`、`F_Nr` 支撑力 |
| 车身 | **LQR + LESO** | 0.001 s（1 kHz） | 平衡、平移 | 腿摆力矩 + 轮力矩 |

两路输出汇合进 VMC → 关节力矩。**这个结构和你现在的控制链几乎可以一一对应**：
他的 MPC 输出 `F_Nl/F_Nr` 就是你的 `Chassis.leg[side].F0`，
他的 LQR 输出腿摆力矩就是你的 `Chassis.leg[side].Tp`。

### 1.1 MPC 模型（极小，这是可行性的关键）

- 状态 `x = [α, α̇, H, Ḣ]ᵀ` —— **4 维**
- 输入 `u = [F_Nl, F_Nr]ᵀ` —— **2 维**
- 预测窗口 `N = 15`

动力学（他的车：`M=26 kg, I=0.64 kg·m², R=0.16 m, b=8 N·s/m`）：

```
竖直：M·Ḧ = (F_Nl + F_Nr)·cos α − b·Ḣ − M·g
横滚：I·α̈ = (F_Nr − F_Nl)·R
```

平衡点 `ᾱ=0, H̄=0.1 m, F̄_Nl = F̄_Nr = Mg/2`，雅可比线性化后得 A、B，
再 ZOH 离散化（`Ts=0.01`）。

**约束**（MPC 的实质价值所在）：
- 腿部力限幅 `20 N ≤ F_N ≤ 150 N`（避免电机过载）
- 力变化率 `|ΔF| ≤ 30 N/步`（防震荡）

### 1.2 为什么是 100 Hz 而不是 1 kHz（**最关键的工程洞察**）

他做了对比实验，结论是**对 MPC 而言，预测时长比控制频率重要**：

| | 1000 Hz | 100 Hz |
|---|---|---|
| 预测总时长（N=15） | 0.015 s | **0.15 s** |
| 能否覆盖外部扰动 | ❌ 覆盖不了 | ✅ 能覆盖 |

跳跃、下台阶的时间尺度是 0.1~0.3 s。1 kHz 下 N=15 只能看到未来 15 ms，**等于没预测**。

**这一条直接决定了 TinyMPC 能不能上你的 STM32** —— 见第三节。

### 1.3 LESO 做什么

解决的是**模型误差**，不是控制律。原文动机：

> 「即使通过模型辨识，真实的系统的模型参数总是会与 LQR 计算时的参数有所区别，
> 同时由于关节减速器的静态摩擦、传动背隙以及腿足落地时的地面弹性形变，
> 在动力学方程中完全未被建模」

做法：把原 6 维 LQR 系统扩张 2 个扰动状态（输入维数=2），

```
X = [x; d],  A_e = [A  B ; 0  I],  B_e = [B; 0],  C_e = [I  0]
X̂_{k+1} = A_e·X̂_k + B_e·u_k + L_e·(y_k − C_e·X̂_k)
```

`L_e` 用**极点配置**求（MATLAB `place(A_e', C_e', poles)`），
然后 **LQR 算出的力矩减去估计的总扰动 `d̂`** 就是最终输出。

实测：Pitch 波动从 3.05° 降到 1.56°，**抑制率 50%**。

## 二、TinyMPC 能不能实现同样效果？——能，而且比 qpOASES 更适合 MCU

他用的是 **qpOASES（active-set）跑在香橙派 Linux 上**，并且原文明确写着：

> 「本人未在单片机端进行 MPC 部署的计算，**对于使用单片机进行控制的同学可以把
> MPC 控制器更改为 LQR 控制**」

—— 也就是说，**他自己认为单片机跑不动，建议退回 LQR。TinyMPC 存在的意义正是推翻这个结论。**

### 2.1 两者的关键差异

| | 他的方案 | TinyMPC |
|---|---|---|
| QP 形式 | **Condensed**：`X = M·x + C·U`，消去状态，只留 `U ∈ R³⁰` 的稠密 QP | **Sparse/结构化**：保留状态，用 Riccati 递推 |
| 求解器 | qpOASES（active-set） | ADMM |
| 复杂度随 N | Hessian 是 `30×30` 稠密，随 N **平方**增长 | 随 N **线性**增长 |
| 目标平台 | 嵌入式 Linux | **MCU** |
| 离线预计算 | 每次重算 Hessian | `Kinf/Pinf/Quu_inv` **离线缓存** |

**TinyMPC 在这个规模上反而更有优势**：它把 MPC 拆成「LQR 反向传播 + 投影到约束集」，
LQR 那一半的增益是离线算好塞进 cache 的，在线只剩递推和投影。

### 2.2 约束怎么映射

- 力限幅 `20 ≤ F ≤ 150` → TinyMPC 的 **input box constraint**，原生支持
- 力变化率 `|ΔF| ≤ 30/步` → 跨时刻耦合，两条路：
  1. **状态增广**：把 `u_{k-1}` 加进状态（4→6 维），变成普通 box 约束
  2. 用 TinyMPC 的**通用线性约束**（`settings` 里有 `en_input_linear` / `en_tv_input_linear`）

推荐先用①，简单且不碰求解器配置。

## 三、可行性评估（数字）

### 3.1 计算量

规模：`nx=4, nu=2, N=15`。TinyMPC 单次 ADMM 迭代主要是沿时域的前向/反向递推：

```
每次迭代 ≈ N · (nx² + nx·nu + nu²) ≈ 15 · (16 + 8 + 4) ≈ 420 次乘加
若封顶 50 次迭代 → 约 10⁵ 量级浮点运算
```

H723 主频 550 MHz、带双精度 FPU。即使按每次乘加 5~10 周期的悲观估计，
**单次求解在亚毫秒到 1~2 ms 量级**。

**而 100 Hz 的预算是 10 ms。余量充足。**

> 对比一下：如果按 1 kHz + 10 维全状态去做，预算只有 1 ms 而计算量是这里的十几倍，
> 那才是不可行。**他 100 Hz 的选择恰好把 MPC 送进了 MCU 的能力范围。**

### 3.2 结论

**可行。** 但有三个必须正视的工程问题：

1. **C++/Eigen**：你的工程是 `enable_language(C ASM)`，全仓库 0 个 `.cpp`；
   TinyMPC codegen 产出 `.cpp/.hpp` 且依赖 Eigen。要么改 CMake 引入 C++，
   要么把 codegen 结果手工翻成 C（4×2×15 规模下工作量可控）。
2. **迭代次数封顶**：ADMM 迭代数据相关。100 Hz 下余量大，但仍须设 `max_iter` 硬上限，
   用「次优但确定」换「最优但不确定」。
3. **`tinytype = double`**：H723 有双精度 FPU 但比单精度慢。这个规模下大概率无所谓，
   实测超预算再考虑改 float。

### 3.3 不可直接照搬的部分

**他的所有数值都是他那台车的**：`M=26 kg`、`I=0.64`、`R=0.16`、`b=8`、
平衡点 `H̄=0.1 m`、力限幅 `20~150 N`。你的大车 `half_track=0.22`（他 0.16）、
质量口径也完全不同。**A、B 必须用你自己的参数重推**，公式可以照抄，数字一个都不能抄。

## 四、建议路线（按性价比排序，不是按他的顺序）

### 第 1 步：坐标变换（半天，不需要 MPC）

把 F0 的装配从「左腿长 PID / 右腿长 PID + roll 差动」改成：

```
共模 H  = (L0_L + L0_R)/2  → 高度环
差模 α  ≈ (L0_L − L0_R)/(2R) → 横滚环
两环输出再逆变换回 F_Nl / F_Nr
```

**这一步就能消掉 PID 打架**，是他整个方案里价值密度最高、代价最低的部分。
做完再决定要不要上 MPC。

### 第 2 步：LESO（性价比远高于 MPC）

**理由**：
- 它是**纯线性代数**，没有求解器、没有迭代、执行时间恒定，1 kHz 在 C 里毫无压力
- 它直接打你已知的最大短板——**MATLAB 与固件参数不一致、`I_z` 偏小、质心未标定**。
  LESO 把这些统统当"总扰动"估出来再减掉
- `LQR_calc.m` 是**现成模板**：`c2d` → `dlqr` → 构造 `A_e/B_e/C_e` → `place()` 求 `L_e`
  → 按腿长多项式拟合。**最后这步和你固件里 `Algorithm_LQR_FitLqrKPoly22` 是同一个套路**，
  基础设施已经有了
- 实测 Pitch 波动抑制 50%

> 顺带：`LQR_calc.m` 里的 `c2d(A, B, 0.001)` 正是你 `ABK_LQR.m` 缺失的离散化环节。

### 第 3 步：MPC（最大工程量，放最后）

前两步做完，再评估 MPC 还值不值得。届时你已经有了正确的坐标和可信的模型，
MPC 才可能发挥它真正的增量：**约束**（力限幅、变化率、提前减速）和**预测**（跳跃、下台阶轨迹）。

## 1. 本轮解决的问题

### 1.1 MPC 求解耗时 50ms → 1ms（已提交 `2dbf042`）

**根因是 `-O0`，不是求解器慢。** TinyMPC 是模板密集的 C++ + Eigen，`-O0` 下模板
完全不展开。修法是 `CMakeLists.txt` 用 `set_source_files_properties` 给
`admm.cpp` / `tiny_api.cpp` / `rho_benchmark.cpp` / `chassis_mpc.cpp` **单独强制 `-O2`**，
业务代码仍是 `-O0`，**烧 Debug 也能让求解器跑正常速度**。Debug 固件 text 从 502976
降到 237300。

⚠ `set_source_files_properties` 是覆盖不是追加，`admm.cpp` 的 `-Wno-unused-variable`
必须和 `-O2` 写在同一次调用里。

**排查教训（重要）**：先后猜错 DTCM 运行时不可读、DWT 软件锁、栈溢出、adaptive_rho、
软件浮点、堆耗尽、setter 值传递、codegen——全不是。真正定位它的是用户的一句观察：
**「solve_us 从 5ms 跳到 50ms，恰好发生在进 STANDING 那一刻」**——那一刻
`Chassis_Control()` 开始满负荷跑，而 `solve_us` 是**墙钟**，45ms 是在等 CPU。
**量墙钟时间时先问"这段时间 CPU 是不是我的"，再问"计算量大不大"。**

### 1.2 MPC 改成独立低优先级任务（已提交）

`Chassis_MPC_Solve(x0,H)` 拆成 `SetInput()` + `Solve(void)`；求解跑在
`chassis_task.c` 的 `MpcTask`（`osPriorityLow`，栈 4096），用 `osDelayUntil` 自定时
100 Hz，**不和控制环握手**。控制环每拍只发布 `x0`、读 `F[]`。
求解慢了只会让自己降频（`solve_count` 增速变慢、`age` 变大），延迟不传导给控制环。
实测 `Chassis.dt_raw_max` 稳定 `0.001`，隔离有效。

⚠ `Chassis.dt` 越界会被钳位回 `default_dt`，**严重超时和正常 1ms 在 `dt` 上分不开**。
判控制环 deadline 只能看不钳位的 `dt_raw_max`。这一条坑过一次。

### 1.3 两个真 bug（已提交）

**a) `rho` 淹没 `R`。** `tiny_api.cpp:337` 的 Riccati 用 `R1 = R + rho`。原来
`R=0.05` 而 `rho=5.0` → `R1=5.05`，**输入权重被放大 100 倍**，等效高度刚度只有
73 N/m（腿长 PID 是 600）。ADMM 理论上收敛后与 rho 无关，但实测 `iter=1` 就退出，
压根没迭代到那一步。修法是把 Q 和 R **同比放大**、让 `R` 与 `rho` 同量级，
不动 `rho`（5.0 在官方期望的 O(1~100) 区间，正是 TinyMPC 自己例子用的值）。

**⚠ 以后改 Q/R 的绝对值时必须连带检查它与 `rho` 的相对大小，只看比值会再踩一次。**
`./Tests/run_mpc_host.sh stiff` 会在 `R < rho` 时直接告警。

**b) `Uref` 错了。** `F_eq = 0.5·body_mass·g`，按 11 kg 算出 54 N，而
`mpc_flag=0` 稳态**实测 `leg[0].F0=31N`、`leg[1].F0=35N`，真实单腿静载只有 33 N**。
差额不是丢了——VMC 把 `(F0,Tp)` 一起映射到关节力矩，腿不竖直时一部分体重由摆角
力矩 `Tp` 承担，不走 `F0`。`R·(F−54)²` 持续把力往 54 拽，而 MPC 没有积分作用补不掉，
刚度越低偏得越多（73 N/m 时偏 29 cm，直接顶到机构限位 0.39m）。

用户已把 `body_mass` 改成 **6.7**（= 2×33/9.81）。⚠ **它不再是机体真实质量，
而是"腿轴向等效支撑质量"**，代码里有详细注释。**重跑 `ABK_LQR.py` 时 `m_b_ac`
必须填机体真实质量（约 11~12.5），不是 6.7。**

## 3. 单腿下台阶：已实现又撤回，结论要记住

做过一版「逐腿接触状态 + 写进 MPC 的 `u_min` 约束」，主机仿真 89ms 达标，
**但按 5cm 行程算的**。用户指出台阶至少 20cm，重算：

```
                    加速度       伸20cm    +检测51ms
79.8 N (ZJU档位)   36.4 m/s²    105 ms     156 ms
150 N  (F_max)     68.5 m/s²     76 ms     127 ms   ← 顶到力上限仍超
100ms 内到位需要   365 N = F_max 的 2.4 倍
```

**这是执行器物理上限，PID 同样做不到，不是 MPC 的问题。** 已整体撤回
（`chassis_observer` / `chassis_mpc` 直接 checkout，其余逐处还原，`grep` 无残留）。

### 撤回时保留下来的三个结论

1. **`all_off_flag` 的入口条件与参考实现相反。** ZJU 式(116)
   `need_flight = ¬on_ground_l ∨ ¬on_ground_r`「任一腿离地即成立」，**是【或】**；
   我们移植成了整车级 `&&`。所以**单腿悬空时三项离地动作一个都不触发**。
   ⚠ **但这对飞坡不是问题**——飞坡是两腿同时离地，`all_off_flag` 正常成立。
2. **`off_F_comp_ratio = 0.28` 偏小。** `Fn_static = 54.3N`（`body_mass` 改小后），
   推力只有 15.2N，ZJU 是**恒定 80N**（对应 ratio ≈ 1.47）。
3. **指标口径可能就不对。** PDF 的原始要求是 **Roll 动态偏差 ≤ 0.085 rad(5°)**，
   「100ms 内伸出」只是它推测的手段。按 roll 判：机体无对抗地倾到 5° 要 89ms，
   这期间腿能伸约 14cm，而且机体自己也在下落、需要的**相对伸长**远小于台阶全高。
   **按真实指标可能是够的**，需要闭环仿真才能定论。

## 4. 下一步：飞坡落地缓冲 + 跳跃

用户已明确选定这个方向（放弃继续追单腿下台阶）。

### 4.1 为什么选它——MPC 的增量在这里才真正存在

站立和 roll 调节上 MPC 和 PID 是一个量级（370 vs 600 N/m，都不振荡），**没有优势**。
而且 Qi-Q26 路线图里价值最高的「共模/差模解耦」早就在 PID 路径里做完了。
MPC 真正的增量只在**约束会起作用**和**有参考轨迹可预览**的场景，正是这两个功能。

### 4.2 飞坡落地缓冲（先做，工作量小）

PDF §3.1.2 原话：

> 针对赛场飞坡后高空落地，算法需在触地前通过腿部行程来进行落地缓冲，利用腿部行程
> 吸收动能，因此要求腿部刚度适中，并且单次落地冲击后车体姿态（Roll/Pitch）不发散，
> 无需反复震荡调节。**通过调整 QR 矩阵来完成此任务**，要求姿态整体收敛时间小于 1s。

**关键：PDF 说这是【调 QR】完成的，不是新算法。** 而且基础设施已经齐了：

- 腾空检测：`all_off_flag` 在飞坡场景正常工作（两腿同时离地）
- 腾空伸腿：现有 `fn_comp` 路径已生效（但 `0.28` 偏小，见 §3 结论 2）
- 落地检测：`land_force_ratio=0.35` + 两路并联判据 A/B，`land_hold_s=0.05`
- 落地交接：`chassis_control.c:1702` 的 `last_all_off_flag` 边沿已经在做
  腿长目标锁存/还原、`leg_length_pid`/`roll_pid` 复位、清 `body.s` 和航向目标

**要做的：**

1. **主机落地冲击仿真**（新增 `run_mpc_host.sh` 的 `drop` 模式）。给定落地速度，
   模拟腿被压缩的过程，量：冲击峰值力是否撞 `F_max`、腿长行程够不够吸收、
   姿态收敛时间。**这是上车前的主判据**，参考已有的 `stiff` 模式写法。
2. **按仿真结果整定 `Q[2]`/`R`**（刚度）和 `Q[3]`（阻尼）。
   ⚠ 改 Q/R 绝对值必须复查与 `rho=5.0` 的相对大小。
3. **`off_F_comp_ratio` 0.28 → 约 1.0~1.47**：腾空时腿要先伸出去，落地才有行程
   可压缩吸能。这一条直接服务"利用腿部行程吸收动能"。
4. 实机：**先小落差**（垫块 5cm 起），逐步加高。

**风险**：落地瞬间关节力矩会撞 `joint_T_limit = 15 N·m` 和 `APP_DM_TOR_MAX`。
`F_max=150N` 折算到关节力矩要用 VMC 的 Jacobian 核一遍，别只看 `F_max`。

### 4.3 跳跃（后做，是真正的新能力）

PDF：「过程中**给定一定时间内的腿长参考轨迹**，即可完成跳跃任务。」

**这是唯一需要动 MPC 接口的地方，也是 MPC 相对 PID 的真增量。** 现在
`chassis_mpc.cpp` 里是

```c
mpcSolver->work->Xref.row(2).setConstant(H_ref);   // 整个时域一个常数
```

跳跃需要把**时变的腿长参考轨迹**填进 `Xref.row(2)` 的各列——`N=15`、`Ts=10ms`，
正好覆盖 0.15s，是蓄力/起跳的时间尺度。接口要从
`Chassis_MPC_SetInput(x0, float H_ref)` 扩成能接受一条轨迹。

**要做的：**

1. 跳跃状态机（蓄力→伸展→腾空→落地），可参考 ZJU 文档 §13 的 Jump 子状态机
   （`/home/quickq/code/STM32/Others/串联腿机器人建模与控制开源文档.pdf`，
   `pdftotext -layout` 后搜 "Jump"）
2. 轨迹生成 + `Xref` 逐列填充
3. 落地沿用 4.2 的缓冲

**风险（PDF 自己踩过）**：「因为轮足步兵车身整体较重，且在电路方面对关节电机
瞬时放电能力补偿不够，**在实测跳跃过程中经常容易电机掉电**」。本车同样要先确认
超电/母线能不能扛住瞬时大电流，**这可能是比控制算法更硬的约束**。

## 5. 工具链

### 主机测试（`Tests/run_mpc_host.sh`，本轮新建）

```
./Tests/run_mpc_host.sh          断言测试 + 堆分配计数
./Tests/run_mpc_host.sh assert   只跑 test_chassis_mpc.c 的断言
./Tests/run_mpc_host.sh malloc   数 Chassis_MPC_Solve 的 malloc 次数
./Tests/run_mpc_host.sh stiff    量等效高度刚度 dF/dH 和稳态力（整定必用）
```

脚本里记了三个坑：DWT 桩头文件、`chassis_config.c` 必须用 gcc 编（C99 数组下标
指定初始化）、`rho_benchmark.cpp` 不能漏链。它还会 sed 出一份 `mpc_flag=0` 的
临时配置副本——`test_chassis_mpc.c` 硬断言了那一位，整定期置 1 会让它首个断言 abort。

**新增 `drop` 模式时照 `stiff`/`malloc` 的写法加。**

### 实机 Watch

```
Chassis_MPC.solve_us / solve_count / iter / F[0..1]
Chassis.dt_raw_max          ← 控制环 deadline 的唯一可信判据（dt 会被钳位）
Chassis.task_stack_free
Chassis.ground.off_ground_flag[0/1] / Fn_ratio[0/1] / fn_comp[0/1]
```

⚠ **读 `solve_us` 时不要暂停调试器**，DWT 数墙钟，暂停时长会被算进去。

### 其他

- **烧录只用 Debug**（`Ctrl+Shift+B`）。per-file `-O2` 之后不需要切 Release。
- 主频是 **480 MHz**（`HSE 24 ÷ M2 × N40 ÷ P1`），历史文档写的 550 是错的。
- MPC 求解环每次约 1400 次 malloc（`tinyMatrix` 动态尺寸），`-O0/-Os/-O2` 数字相同。
  **实测只占耗时约 1.5%，不值得为它改 TinyMPC 源码。**

## 6. 挂着的前置项

1. **`Chassis_MPC.age` 只观测不参与控制**：MPC 跟不上时控制环仍用陈旧的 `F[]`。
   需要决定陈旧到多少拍退回 PID 路径。
2. **`I_roll = 0.324` 和 `damping = 8.0` 都是估算值**，从没实测过。

3. **`driver_uart.c:31` 的 `-Warray-bounds`** 挡着 Release 的零警告门槛。
   已确认误报，修法涉及风格判断（加 NULL 检查违反"不写防御性代码"），未动。
4. **`lqr.L0_min/L0_max = 0.10/0.35` 与 `ABK_LQR.py` 的采样区间是否一致，未复核。**
   `body_mass` 改成 6.7 之后与 MATLAB 的对应关系已断，见 §1.3。

# 交接文档 2026-09-24 07:40

> 范围：**云台** | 上一份：`handoff-2026-09-24-0619.md`（范围：云台）

发射机构长期计划的**第一步**：四台电机能收发，三个摩擦轮跑起 PI 速度环。
拨盘本步只做到通信。键位语义一个字没动。

---

## 1. 硬件与旧代码假设不一致，全部按实际改了

旧代码是照"两个 M3508 摩擦轮 + 一个 M2006 拨盘，全挂 FDCAN2"写的。实际：

| | 旧假设 | 实际 |
|---|---|---|
| 摩擦轮 | 2 × M3508 / C620 | **3 × M2006 / C610** |
| 拨盘 | M2006，FDCAN2 | M2006，**装在底盘上，挂 FDCAN3** |

拨盘挂 FDCAN3 是因为它物理装在底盘、却要由云台控制——那是两板之间唯一的线。
于是**发射机构跨两条总线**，各有一个 0x200 帧（同 ID，不同总线，互不干扰）。

---

## 2. ⚠ 总线负载是这一步的硬约束，不是事后优化

先把基本参数钉死：FDCAN 内核时钟 = 24 MHz / PLLM 2 × PLLN 40 / PLLQ 4 = **120 MHz**，
位定时 `(1 + 29 + 10) × 3 = 120` 分频 → **1 Mbps**。标准帧 8 字节无位填充 111 位、
最坏填充 135 位，**上限只有 7400~9000 帧/s**。

| 总线 | 组成 | 帧/s | 负载 |
|---|---|---|---|
| FDCAN2 | 3×M2006：1 控制 + 3 反馈 @1kHz | 4000 | 44% ~ 54% |
| FDCAN3 | 2×DM4310 MIT 4000 + 拨盘 2000 + 板间 400 | 6400 | 71% ~ 86% |

**`APP_BOARD_SEND_DIV` 从 1 改回了 5。** 这是本步的必要条件：不改的话板间占
2000 帧/s，FDCAN3 合计 8000 帧/s、最坏 108%，**超容量**。200 Hz 不丢信息——
接收机帧率本来只有 71~143 Hz，1 kHz 是 7 倍过采样。

⚠ 上一轮那份 handoff 里"板间 DIV=1 是用户有意设的，别改回去"这句**已经作废**，
原因就是拨盘上了 FDCAN3。

⚠ 订正一个此前被当作依据的数字：底盘 **FDCAN1 是 2×DM + 2×DJI 轮 = 7000 帧/s
（78%~95%）**，不是 4 个 DM。它本身就在边缘，不能拿来论证"还有余量"。

## 3. C610 ≠ C620，两处不兼容（手册对出来的）

`Material/RoboMaster  C610 无刷电机调速器使用说明.pdf`：

| | C620（底盘轮电机） | **C610（发射机构）** |
|---|---|---|
| 反馈 `data[6]` | **温度** | **空** |
| 反馈 `data[7]` | 空 | **电机错误码** |
| 控制电流量程 | ±16384 = ±20 A | **±10000 = ±10 A** |

原来的 `device_motor_dji.c` 把 `data[6]` 当温度解——那是 C620 的格式，全换 M2006
之后那个字段恒为 0，而**错误码白扔了**。错误码里有**堵转**（`MOTOR_DJI_ERR_STALL`），
拨盘卡弹就是它，已接进 `SHOOTER_FAULT_ESC`。

⚠ **底盘那份 `device_motor_dji.c` 是独立副本、仍是 C620 口径，没动也不要动。**

电流量程这边原来**完全没有限幅**，本步补上（限幅是风格规范里的安全红线）。

## 4. ⚠ 未装机的总线一帧都不能发

`gimbal_control.c` 里原本记着一条坑：某条总线上一个节点都没有时，发出去的帧没人
应答 ACK，发送错误计数爬到 BusOff，驱动 Stop/Start 恢复再 BusOff，**空转在错误恢复里**。

发射机构跨两条总线之后这条更要紧了，所以
`Motor_DJI_UpdateTxFrames(fricBusEnable, triggerBusEnable)` 带两个参数，
由 `Shooter_Config.output.fric_flag` / `trigger_flag` 驱动，**两个都从 0 出厂**。

**这两个参数看着像多余的防御，实际是分步装机的唯一手段。** 单测里
`testBusEnableGating` 钉死了"使能为 0 的总线一帧都不发"，把它改成无条件发会变红。

## 5. 结构改动：发射机构拆成独立模块

新建 `3_Chariot/1_Module/Shooter/`，与 Gimbal 平级，由 `gimbal_task` 并列调用。

从 Gimbal 模块里摘走了：`I_dji_req/I_dji`、`fric_flag/trigger_flag`、
`GIMBAL_FAULT_DJI`、`Gimbal_Config.output.dji_flag`。

**直接动机**是分层：同层模块不能互相调用，发射机构的输出门留在 `Gimbal_Config`
里 Shooter 就读不到。**顺带修掉一个真实缺陷**——原先 `GIMBAL_FAULT_DJI` 会置
`Gimbal.safe_flag`，也就是**一台摩擦轮掉线连云台瞄准都做不了**。现在两者各有
自己的 fault 和 safe_flag，互不封锁。

`CAN_Task_SetDjiCurrent()` 也从 `task_can.c` 删了，发送逻辑收回设备层，
与 `Motor_DM_SetCommand / UpdateTxFrames` 对称。`task_can` 现在与 DJI 完全解耦。

### 摩擦轮速度环有一处要提前说明

用的是 `Algorithm_PID_UpdateByFeedbackRate()`——仓库里唯一的 PID 更新函数，
它取 `derivative = -feedbackRate`。**速度环 `kd = 0`、`feedbackRate` 传 `0.0f`，
整体退化成 PI**。那个 derivative 本意给"反馈速度可信"的位置环用，速度环的导数
是加速度、没有可信来源，所以不给。**这不是漏传参数**，配置和调用处都写了注释。

⚠ 反馈 `speedRpm` 是**转子**转速，M2006 减速比 36:1，输出轴要除 36。
目标转速统一用转子口径，不引入第二个单位。

## 6. 验证

| 项 | 状态 |
|---|---|
| 云台三后端各 `--clean-first` | ✅ 各 0 警告 0 错误 |
| 底盘 `--clean-first` | ✅ 0 警告 0 错误（确认没被波及） |
| `test_motor_dji`（新增 9 组） | ✅ 过，**9 个变异全部被抓住** |
| 其余 15 个主机单测 | ✅ 全过 |
| **实机** | ❌ **一次都没上** |

变异覆盖：错误码读 `data[6]`（照抄 C620）、反馈不比总线只比 ID、
拨盘/摩擦轮互相塞错帧、去掉电流限幅、两个 busEnable 各自被忽略、
安全门失效、摩擦轮帧发到 FDCAN3 —— 全部变红。

⚠ **`testTwoBusFramesIndependent` 是这个单测最要紧的一条。** 两条总线上的帧
ID 都是 0x200、长度一样、肉眼分不出，把拨盘的电流写进摩擦轮那帧会直接控错电机。
给四个互不相同的电流值逐槽位核对才抓得住。别为了"简化"把它改成全填同一个值。

## 7. 实机分三步走，别一次全上

1. **两个门都关着**，只看反馈。确认四台 `Shooter.motor[].isOnline` 为 1、
   `errorCode` 为 0、用手转摩擦轮能看到 `speedRpm` 变化。
   **同时看 `CAN_Task_GetTxErrorCount()` 和底盘的 `Chassis.can_error_count`**——
   这是板间分频改动和新增总线负载的第一道判据。
2. 开 `trigger_flag`，`Shooter.enable_flag = 1`，`trigger_I_manual` 从 0 慢慢加到
   几百，确认拨盘转、方向符合预期。
3. 开 `fric_flag`，`fric_target_rpm` 从 0 起整定 PI。
   ⚠ **摩擦轮必须先装好防护再通电**，三个轮同时起转动能不小。

`Shooter_Config.fric_speed_pid` 那组参数是按 C610 手册的性能曲线推的量纲，
**完全没有实机依据**，第一次上机从小 kp 起。

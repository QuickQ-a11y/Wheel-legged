# 代码风格要求

## 必读

- 每次写代码前，先阅读本文件。
- 新增要求直接追加到对应章节；没有合适章节时，新建短标题。

## 总原则

- 优先简单、直接、可读。
- 不为了“封装”而封装。
- 不保留未使用的函数、变量、宏或中间状态。
- 修改前先看现有结构，优先沿用当前工程风格。
- 应用层类型使用 `Pascal_Snake_t`，例如 `Chassis_Leg_t`、`Chassis_Output_t`。
- 高层函数使用 `Pascal_Snake_Case`，例如 `Chassis_State_Update()`、`VMC_State_Calc()`。
- 应用层成员、参数和局部变量使用 `lower_snake_case`；布尔量统一使用 `*_flag`。
- 全局主实例使用首字母大写的职责名，例如 `Chassis`、`Chassis_Config`。
- HAL、设备层、算法库和已有公共接口保持所属模块风格，不做跨层机械重命名。
- 宏和枚举值使用模块前缀大写命名，例如 `CAN_TASK_PERIOD_TICKS`。
- 不新增统一 status 类型、统一错误码枚举或跨模块状态返回体系。

## 长期调试与易 Debug

## 宏命名

- 宏名使用模块前缀和短语义的大写 `snake_case`，下划线通常不超过 3 个，例如 `APP_DM_PMIN`。
- 名称应短而明确：使用工程约定缩写 `CMD`（控制）、`FB`（反馈）、`POS`（位置）、`VEL`（速度）、`TOR`（力矩）。
- 不重复表达同一层级语义：使用 `CMD`，不要使用冗长的 `COMMAND`；使用 `FB`，不要使用冗长的 `FEEDBACK`。
- 数值边界统一使用 `MIN`、`MAX`；单位优先写在注释中，只有不超过 3 个下划线且确实能提高辨识度时才放入宏名。
- 电机位置缩写使用 `LF/LB/RF/RB` 表示左前、左后、右前、右后；控制器 ID、方向和物理单位必须在相邻注释中说明。
- 不使用无法从上下文确定含义的名称，例如 `X1`、`P2`、`VALUE_A`；也不省略会影响单位或数据方向判断的关键部分。
- 同一组范围宏必须保持对称命名，例如 `APP_DM_PMIN` 与 `APP_DM_PMAX`。

## 物理符号

- 控制公式优先采用上交模型和轮腿工程共同符号，不展开成重复单位长名。
- 五连杆使用 `l1~l5`、`phi0~phi4`、`L0`、`d_L0`、`d_phi0`。
- 十维模型使用 `s`、`d_s`、`fai`、`d_fai`、`theta`、`d_theta`。
- 广义控制量使用 `F0`、`Tp`、`T_wheel`、`T1`、`T4`，轮电流使用 `I_wheel`。
- 几何关节统一使用`phi1/phi4`，物理电机和传动杆位置才使用`front/back`。
- 每个DM关节用`scale`定义方向、用`ratio`定义主动杆角/电机角传动比；位置、速度和力矩统一消费`scale*ratio`，设备层不得再维护安装方向。
- 目标、上一周期和二阶导数分别使用 `target_*`、`last_*`、`dd_*`。
- 短物理符号必须在结构体字段注释中写明单位和方向；硬件反馈、协议字段及跨模块接口仍保留必要的 `rad`、`rpm`、`nm` 等单位信息。

- 本工程定位为长期调试、长期修改、长期优化代码，优先保证可修改性、易 Debug 和主流程直观。
- 参考 SPR 的代码风格，固定调用链中已经明确的数据来源，不反复增加 `enable`、`valid`、`status`、`Is`、`Check` 这类中间状态或查询函数。
- 只在当前消费位置使用一次的布尔条件直接写成 `if`，不提前保存为 `bench_flag`、`output_flag` 等派生状态。
- 流程型函数默认使用 `void`，不通过 `app_status_t` 或大量 `uint8_t` 返回值表达普通控制流。
- 调试阶段允许保留必要临时变量和 Watch 友好的全局快照，但不要为同一份事实额外复制多套结构体。
- 不为了兼容理论上的错误输入写大量防御性代码；主流程应直接表达“数据从哪里来、计算什么、输出到哪里”。
- 实机安全底线必须保留，包括电机限幅、上电零输出、离线保护、数组边界、除零保护、腿长范围、几何奇异、CAN/IMU/电机安全链路。

## 函数

- 应用层函数使用“职责 + 动作”的 `Pascal_Snake_Case`，例如 `Chassis_Control()`、`Chassis_Recovery()`。
- 算法 API 保留稳定大写缩写，例如 `VMC_Torque_Calc()`、`PID_Init()`、`LQR_Calc()`。
- 文件内静态辅助函数使用短 `Pascal_Snake_Case`，不重复文件已经表达的模块前缀，例如 `State_Enter()`、`Limit_Symmetric()`。
- 测试辅助函数使用 `lower_snake_case`，例如 `assert_zero_output()`、`test_recovery_handoff()`。
- HAL、CMSIS、CubeMX 生成接口、第三方库和外部参考工程原始接口保持原名，不做风格性重命名。
- 只有在明显复用、隔离模块边界、或降低主流程复杂度时才新增函数。
- 一两行的简单表达式优先直接写在调用处。
- 函数名说明动作，变量名说明含义。
- 模块公共接口默认使用 `void`，不通过统一 status 返回值表达成功或失败。
- 不把旧的 `app_status_t` 替换成大量 `uint8_t` 成功/失败返回值；流程型函数尽量使用 `void`。
- 不为了规范化新增 `Is`、`Get`、`Check` 这类简单查询函数；简单条件优先直接写在使用位置。
- 固定内部调用链已经保证有效的指针，不重复写 `NULL` 防御判断。
- 真实安全约束必须保留，例如上电安全输出、设备在线、数组下标、腿长、限幅和几何奇异判断。
- 任务初始化入口可保持 `void`，以兼容 CubeMX/FreeRTOS 已生成调用链。

## 注释

- 新增注释必须使用中文。
- 注释解释协议、边界、原因和非显然逻辑。
- 不注释一眼能看懂的赋值或判断。
- 结构体字段、状态机步骤、硬件映射和关键局部变量应写清楚用途或单位。
- 函数注释使用 Doxygen 块格式：

```c
/**
 * @brief 用一句话说明这个函数或模块做什么。
 *
 * 补充说明协议格式、边界条件、调用约束或设计原因。
 */
```

- 变量、结构体字段、局部映射用普通中文短注释即可。

## 嵌入式 C

- 驱动层只处理硬件收发，不写业务解析。
- 任务层负责调度、分发和模块连接。
- 设备层负责解析和维护设备状态。
- 驱动层 HAL 调用失败不向上层传播统一错误码，上层安全保护依靠设备在线状态、故障位和安全零输出链路。
- 协议 ID 可在分发处直接列出，保持映射清楚。
- 硬件映射、设备数量、总线 ID、超时阈值等常量集中配置，避免散落在多个模块。
- 上电默认安全零输出；关键设备异常时持续覆盖零电流或零力矩。
- 高频任务使用固定周期或明确超时，不在控制环中做动态内存分配。
- 需要长期在 Watch 窗口观察的关键任务状态，优先把原有状态快照以带 `Debug` 的清晰命名暴露为全局变量；不要为同一份事实额外复制一套 debug 结构体。
- 暴露给 Watch 的状态快照只作为调试入口，业务代码仍优先通过模块已有接口读取，避免形成新的跨模块依赖。

## CAN 发送

- CAN 发送接口不等待 ACK、不等待发送完成、不重发失败帧。
- FDCAN 自动重发默认关闭；如果 CubeMX 重新生成代码，需要确认 `AutoRetransmission = DISABLE`。
- 单帧发送失败、发送队列满或 HAL 添加发送请求失败时，直接跳过当前帧，后续周期继续发送最新命令。
- 驱动层允许在 BusOff 时做轻量 stop/start 恢复，避免总线错误导致后续发送永久停止。
- 只接 CAN 分析仪调试时，分析仪必须工作在会 ACK 的正常模式；静默监听模式不会应答 ACK。

## USB 通信

- 当前开发板使用 `USB_OTG_HS` 的内部 Full Speed PHY，物理引脚为 PA11/USB_DM、PA12/USB_DP，USB 时钟使用 HSI48。
- 内部 Full Speed PHY 不启用 USB DMA；接收中断只复制字节到环形缓冲并唤醒任务，CRC、协议解析和业务分发放在 USB 任务中执行。
- USB CDC 是连续字节流，不把单次 OUT 回调当成完整协议帧；协议解析必须支持半帧、连续多帧、前置无效字节和校验错误后的重新同步。
- 协议 SOF 固定为 `0xA5`，CRC8 校验 `sof/data_length/seq` 对应的前 4 字节，CRC16 校验除末尾 CRC16 外的完整数据包，16 位字段统一低字节在前。
- 发送状态帧使用固定容量 FIFO 和批量 CDC 传输；队列满、USB 未连接或发送失败时丢弃旧数据，不阻塞控制任务、不反复重发过期帧。
- `cmd_id` 属于业务定义，USB 驱动和通用协议层不得硬编码具体命令号。
- 业务 payload 的封包和解包必须逐字段显式书写，不使用整结构体 `memcpy()` 或字段循环；CRC、环形缓冲、流式解析和批量发送所需的循环与内存搬运保留。
- 发送封包直接给 `packet->header`、`packet->payload` 和 `packet->crc16` 成员赋值，不使用字段写入辅助函数和偏移量计算增加跳转层级。
- USB 驱动、协议、任务和调试变量统一使用 USB 自身语义命名，不使用 `chassis` 或其他业务模块前缀造成归属混淆。
- USB 模块保持独立，只通过其他模块的公开数据接口获取待发送数据，不访问其内部变量，不把底盘控制或其他业务计算写入 USB 代码。

## 坐标系

- 整车业务层统一使用右手系：X 前、Y 左、Z 上，角度和角速度按右手定则为正。
- BMI088 原始数据快照保留传感器原始坐标，便于硬件排查；IMU 任务对外输出的姿态角、角速度、运动加速度和零偏必须转换为整车右手系。
- 当前 IMU 内部坐标到整车右手系按 Z 轴镜像处理：roll/pitch 取反，yaw 保持不变；gyro X/Y 和运动加速度 Z 同步取反。
- 底盘、整车控制、LQR、VMC 和后续模块默认接收整车右手系数据，不在各模块内重复做左右手系转换。
- 如果某个控制模型状态定义与整车右手系相反，只在对应模型配置的 scale 中改符号，不在任务层、控制器或系数表中临时反号。

## 头文件

- 头文件统一顺序：保护宏、`extern "C"`、`include`、宏定义、类型定义、`extern` 变量、函数声明。
- 头文件只暴露模块边界需要的类型和函数，不暴露内部静态状态。
- 新增公共基础类型优先放在公共头文件中，避免任务层和设备层互相依赖。

## 结构体与数据所有权

- 业务结构体按职责组织，不按 `float`、`uint8_t` 等数据类型组织。
- Chassis 只维护唯一运行实例 `Chassis_t Chassis`，也是长期 Watch 入口，不复制第二套 debug 状态。
- `Chassis.body` 拥有整车运动状态，`Chassis.leg[2]` 拥有单腿几何、目标和广义力，`Chassis.goal` 拥有外部运动目标。
- `Chassis.lqr` 只保存十维接口、K 和缩放；物理输出写入 `Chassis.leg[].F0/Tp` 和 `Chassis.output.T_wheel`。
- `Chassis.output` 同时保存控制请求和安全门后的最终命令；设备故障不得阻断请求量计算，只清最终命令。
- 每个跨周期事实只保留一个所有者。VMC 只更新运动学字段，不清除同一腿对象中的目标和控制量。
- 函数收到结构体参数后只消费参数，不再混用同一数据的全局实例。
- 只有确实跨周期的数据使用 `static`；普通中间量和循环索引不得使用 `static`。

## 轮腿控制参考

- 修改轮腿控制代码前，除阅读本文档外，还必须阅读当前工程的 `chassis_control.c` 和 SPR 参考工程的 `chassis_control_loop()`。
- SPR 参考路径为 `E:\AWL_WORK\Wheel-legged\Others\SPR Balanced-infantry\SPR Balanced-infantry\code\chassis\chassis`，重点参考 `Task/chassis_task.c` 中的 `chassis_feedback_update()`、`chassis_control_loop()` 和 `chassis_stay_STANDING()`。
- 参考 SPR 时只参考已验证的控制流程和数据流，不直接照搬状态机、参数、遥控逻辑、功率限制、跳跃、自起身或 KNN 检测等未接入本工程的功能。
- 参考 `DM-balance机加工版本` 时只学习浅调用链、直接物理命名和主流程写法，不把其左右两套六维控制器移植到本工程。
- 当前控制模型固定为一套十维整车模型，状态顺序必须保持 `[s, dot_s, fai, dot_fai, theta_l, dot_theta_l, theta_r, dot_theta_r, theta_b, dot_theta_b]`，输出顺序必须保持左轮、右轮、左腿摆、右腿摆。
- 底盘按职责保留 `config/control/vmc/observer/remote`；文件拆分必须对应真实算法或输入边界，禁止纯转发包装层。
- 使用唯一全局实际状态 `Chassis_t Chassis` 作为控制状态和 Watch 入口，不再维护 controller/debug 副本或重复 getter。
- 公共控制入口使用 `Chassis_Init()`、`Chassis_Leg_Update()`、`Chassis_State_Update()`、`Chassis_Control()`、`Chassis_Recovery()`、`Chassis_Bench()` 和 `Chassis_Step()`。
- 轮腿控制主流程保持清楚的单向链路：设备反馈 -> 腿部几何状态 -> 速度融合和十维状态 -> 支撑力 -> 双腿长 LQR K -> 四路广义输出 -> VMC -> 电机命令。
- `Chassis_Control()` 中十维状态集中赋值，四组十维 LQR 统一点乘；不要拆成只做搬运的 BuildState、BuildLqrK、ApplyOutput 包装。
- 从 `chassis_task` 到具体控制公式的阅读跳转尽量不超过三次；只有 VMC、PID、Kalman 和 LQR 这类明确算法边界允许独立文件。
- 机械参数、IMU 轴向、电机方向、限幅和 LQR 拟合系数集中放在 `chassis_config.c`，不要在任务层、设备层或控制器临时补硬编码。
- 定腿长调试和变腿长控制始终使用实时左右 `L0` 拟合K；固定目标腿长不允许通过伪造K输入实现。
- 安全零输出链路必须保留；未确认实机方向、限幅和输出开关前，不允许打开非零电机输出。
- `chassis_task.c` 每轮按“反馈更新 -> 腿状态更新 -> 状态选择 -> switch-case -> 命令发送”执行；设备故障只在最终命令阶段覆盖零力矩和零电流。
- 不得在任务层写临时固定电机命令覆盖控制器结果；调试固定输出必须由用户明确要求，并在调试结束后立即删除。
- 当前底盘任务目标周期为 1 ms；控制器使用任务实际 tick 差得到的 `Chassis.dt`，越界时回退到 `Chassis_Config.default_dt`。
